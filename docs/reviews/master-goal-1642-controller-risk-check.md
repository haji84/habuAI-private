# Task7 pre-implementation risk check

Read-only review of the persisted controller/continuation plans and current bridge/orchestrator. Direction is sound; the following concrete seams need explicit contracts before implementation. No new service, credential or permission is needed. Detailed bridge security remains governed by its approved Task5 review.

1. **High: root accounting cannot reuse current per-run budget semantics unchanged.** master_orchestrator initializes round_number=0 for a new scientific run; bridge hardcodes300seconds and keys shared receipts/checkpoints solely by run_id. Adding a root elapsed floor alone still resets rounds/candidate admission after code changes. Define one authoritative root ledger with used/reserved seconds, consumed round IDs, preregistered selectable recipe IDs and job/strategy attempts. Reserve round/candidate/time together before execution, settle exactly once by attempt ID, and reject overflow. Pass explicit inherited round/candidate context into the parent, not just JSON metadata. Tests must show changed code cannot reset any bound.

2. **High: scientific cache identity and campaign execution identity must be distinct.** Identical inputs/code currently share a run receipt and checkpoint across different issues. A root-specific budget floor/round context would make those shared result budgets inconsistent, and replaying a cached terminal result must not double-charge compute or inherit another campaign's authority. Keep a content science identity for reusable immutable evidence and a root/operation-bound execution receipt/ledger. Either prohibit cross-campaign checkpoint reuse for continuations or explicitly validate evidence-only reuse and account only work actually executed. Do not alter immutable cached manifests to inject the new root.

3. **High: root reservation, canonical child and lease ownership need one CAS transition.** A separate child claim followed by a budget write leaves a crash window for double execution or stranded allowance. Record operation ID, canonical child issue, attempt/fencing generation, source and reservation in the same append-only root-ledger commit. Use direct-parent non-force remote ref publication; local flock/global Actions concurrency does not serialize the active chat writer. On crash, never release reserved compute merely because lease expired while the old worker may still run: fence completion/publication by generation and conservatively charge the prior bounded allowance unless a verified checkpoint permits exact reconciliation. Every settle/release is idempotent.

4. **Medium: canonical child selection cannot change after execution starts.** 'Deterministic canonical issue' is underspecified when an earlier-numbered issue is discovered later after ambiguous creation. Let first successful root-ledger CAS claim fix the canonical issue irrevocably; all other owner-authored matching issues are duplicate transports. Do not recompute the winner by minimum issue number after a claim. Reconciliation queries need explicit pagination/completeness; search absence from one page is not absence. Issue duplication is tolerable; duplicate scientific execution is not.

5. **High: accepted GitHub facts must be fetched by the actual privileged operation.** An injectable transport plus a CLI accepting fact JSON can accidentally make committed/self-consistent PASS receipts the production admission path. Specify the concrete active-chat operation sequence: direct authenticated GitHub reads, exact current PR/head/workflow/attempt/review checks, clean independent verifier execution, immutable result persistence, and actual merged default-source verification before continue_backend. The helper may plan/validate operations but cannot label arbitrary saved input as authenticated. Test fake transport only through explicit test harness; ordinary invocation must not enable it via flag/environment. Existing authenticated owner issue supplies command authority, not truth of scientific/CI claims. Task5 HANDLED or a valid report-tree/hash chain never substitutes for these checks.

6. **Medium: source reconciliation must not edit the immutable child command body or old source pin.** A child can be created while main subsequently advances. Once command text/receipt is bound, do not revise its required SHA in place. Reconcile via a new immutable intent revision and subordinate transport issue under the same logical continuation operation/root reservation; supersede the old transport before execution. Once claimed, retain that source if still trusted history as Task5 does. Define whether compatibility accepts an exact verified relevant closure or requires a fresh accepted result; do not silently run arbitrary current main. Handler deployment on actual main is a required precondition, not satisfied by local code.

7. **Medium: useful-job admission needs a stable capability key, not a version-dependent request hash alone.** An unmet requirement can recur after source/docs/evidence changes and yield a new request hash. Bind implementation-completeness jobs to canonical requirement+approved capability scope+campaign, retaining equivalent failed-strategy/attempt history across those versions. Admission must check the actual installed adapter/capability registry, not merely a model's free-text blocker or a stale matrix row. Missing data produces no code job unless an explicit scoped missing ingestion/executor capability is independently observed. Terminate/reject already-implemented or unsupported inferred jobs rather than endlessly opening PRs.

8. **Medium: RETURNED must distinguish code acceptance, merge and backend continuation.** A verified PR candidate can be RETURNED_TO_VALIDATION before merge, but it is not deployed for the existing Actions bridge. Define separately PR_VERIFIED, MERGED_SOURCE_VERIFIED, CONTINUATION_CREATED/CLAIMED and BACKEND_RETURNED, or equivalent explicit result substates. Current linear plan can otherwise mark RETURNED after CI and stop without executing the child. Live acceptance must reach an authenticated new backend result automatically, linked to original command, with no second owner prompt. Data-blocked child science is a valid observed result; a docs-only handoff or unopened pending operation is not completed execution.

Minimum additional regressions: two controllers plus Actions root-CAS race; late discovered duplicate issue; old worker completion after lease takeover; crash between reservation and child receipt; exact once settlement; same science ID under two roots; code change preserving exhausted round/strategy ledger; invalid partial-page absence; source advancement before versus after claim; production helper rejecting caller-authored fake GitHub facts; useful mapped completeness job reaching actual merged-source child run. No automatic wake-up after Work-session termination should be claimed.
