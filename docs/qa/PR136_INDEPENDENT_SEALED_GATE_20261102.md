## 結論

既存の固定40件は全内容が開発側に公開・観測されたため、その再試験を未見評価にしない。新しい評価を実行するには、**実装者と別の正当な管理者が、コード・モデル・閾値を凍結した後、非公開の新規合成ケースを作成**する必要がある。既知40件のテンプレートや既存ログを流用して一般化性能を主張しない。

現在のGitHubリポジトリはpublic。ラベル・期待値・固定例証を公開PRへ保存すると未見の条件を破る。認証や新規privateストレージを勝手に有効化しない。現時点でその保管先と署名権限は実証されていない。**GitHub Actionsの通常PASSも、独立署名と独立実機実行の代わりにはならない。**

## 4段階のコミット・リビール

1. **FREEZE**: 開発側が実際のPR HEAD、Qwenモデルdigest、reviewer/prompt/scorer/executorのSHA-256、既存閾値（Precision>=0.95, Recall>=0.80, Clean false-alert<=0.05, critical miss=0）を確定し、署名する。ケース作成や正解公開より前でなければならない。
2. **CASE SEAL**: 実装者と異なる独立custodianが、固定コードに依存しない新規40件以上の合成ケース（BUG>=20、CLEAN>=20）を用意。Python/JS各8件以上、少なくとも1件の重大欠陥を含むこと。ソースSHA、仕様、固定入力、独立実行の観測値・必要動作、証拠ハッシュを保存し独立署名。公開モデル入力は`case_id/path/patch/source_sha256`だけ。正解、critical属性、固定入力、観測値、対になる正常例を出さない。
3. **PREDICTION COMMIT**: 開発者と別のcollectorが全ケースのモデル生回答を署名し、ケース集のSHAに結び付ける。全件・欠測・棄権・誤警告を記録。回答は出典ソースハッシュ、引用行、モデル応答SHAに結びつけ、後から結果に合わせて編集できないようにする。入力や出力が欠けた事例は「清潔な正常例」にしない。
4. **ADJUDICATE / REVEAL**: 別の独立reviewerが固定実行の署名済み証拠とモデル主張の入力/実結果/必要結果の一致を照合し、指摘ごとに REPRODUCED / REFUTED / INCONCLUSIVE を記録。CASE / PREDICTIONS / ADJUDICATIONS の署名・SHAチェーンを検査してからラベル照合。正常への生警告は内容に関わらず偽警告として計上し、欠陥で根拠確認された主張だけをTPとする。すべての生指摘をPrecision分母へ含め、確認できない指摘はTPとしない。全件沈黙ならRecall=0。重大欠陥の見逃し0も必須。

## 実装で確認した秘密情報の分離不足と対策

最初の試験コードではモデル回答collectorがprivate `cohort` オブジェクトを受け取っていた。モデルへ渡す関数でlabelを除去しても、collectorのプロセスが密封済み正解や固定観測を読める状態では、独立評価の保管境界を満たせない。この欠陥をREDテストとして再現し、修正した。

現在の契約ではcustodianだけがprivate `cohort` と署名鍵を扱う。custodianが別途、`stage=public` のHMAC付き公開ケース封筒を発行する。モデルとcollectorが扱えるのは公開ケースの`case_id/path/patch/source_sha256`と非秘密のコミットメントSHAだけ。collectorはprivate cohortやcustodian鍵を必要としない。

採点担当はprivate cohortとpublic envelopeの両方のHMAC・元SHAを確認し、公開ケースをprivate正本へ一対一で照合する。改ざん、余分なラベル、隠れた正解、公開ケースの差し替え、予測コミット後の変更はすべて不合格にする。HMACを検証するためのcustodian鍵はcollectorへ提供せず、採点担当のみが信頼された別の経路で受け取る必要がある。**署名があるだけでは、実際に別の管理者が鍵を持っていたことまでは証明できない。**

## 安全な境界

`sealed_eval_protocol.py` はstdlibによるHMAC/SHA-256とスキーマ検証だけを実装する。**モデル出力コード、元PR、任意のモデル提案入力を実行しない。** ラベル、仕様、実行証拠を外部から提示しただけで勝手に信用せず、与えられた鍵で改ざんを検証する。HMACはその鍵を持つ者による署名の確認であって、**本当に別の人間や別モデルが管理していた証明ではない**。鍵保有者と実行過程の独立性は、別の監査ログ・権限分離・実行証人が必要。

ユニットテストの40件は**全部同じ単純な合成コードを使う模擬データ**。公開されたテスト鍵は偽物。モデルの未見精度でも、本番コードのバグ発見率でも、独立評価の成果でもない。テストの完全正解100%でも `quality_qualified=false` を固定し、署名付きで各指標が良い場合にも `INDEPENDENT_REVIEW_BLOCKED` を返す。

## 追加のモデル出力・ソース完全性検証

密封privateケースのソースと、モデルへ提示するunified diffの追加行が完全一致していることを必須とする。パスやソースSHAだけを一致させ、別のコードをdiffとしてQwenへ見せてから正解をすり替える方法を拒否。ラベルのcritical属性はBUGだけに限定し、閾値の`False == 0` の暗黙一致も拒否する。指摘を再現済みとして採点する場合、モデルが提出した実行コード行の引用が実際に一致していることも必要で、コメントや架空の行を根拠にした再現認定は禁止。

**これらは採点器の改ざん耐性・証拠整合性であって、モデル自体の推論精度向上を意味しない。** 実モデルに正しい説明を作らせたかどうかは、独立した新規合成評価で改めて実証する。

## 残っている実行条件

- 既知6件スモーク、研究用既存40件、最新HEAD CIの各ゲートの本物の結果

`QUALITY_QUALIFIED` にはできない。開発中は `QUALITY_HOLD`、独立封印未成立は `UNSEALED_HOLD` と併記。もし署名用鍵やprivate領域を作れない環境なら、無理にラベルをPRへ置かず、その条件を具体的なブロッカーとして記録する。
