# Task8: trusted reproduction, reviewed activation and future issuance

Read-only design based on integration notes, current champion_registry.py/issue_prediction.py, normative controller/composite designs and exposed GitHub connector contracts. No remote mutation or live capability probe performed. This is implementable conditional production logic, not an assertion that current data can pass its gates.

## Authority boundary

Use the existing owner-authorized active Codex controller as the privileged coordinator. It obtains GitHub facts directly through the authenticated connector, runs independent reproduction in a clean pinned workspace, and proposes an activation intent through the existing branch/review/CI/PR path. Actions remains the existing backend. No Compass service, new token, signing service or Actions permission is required.

Trust roots are the existing authorized controller, authenticated GitHub transport, reviewed fixed production code/policy and reviewed repository history. Hashes only bind content. Ordinary JSON supplied by a candidate, reports on an arbitrary branch, local current.json, an environment variable naming GitHub, or a Python `trusted=True` parameter cannot establish those roots.

This is not cryptographic protection against an attacker already controlling the authorized controller, its credentials, reviewed main code or production process. An in-process opaque context also cannot sandbox arbitrary Python with equal privileges. State that boundary; do not solve it by pretending an object constructor proves external authenticity. Data-only callers and candidate code must never run inside the privileged verifier/writer process or obtain its connector transport. Production entrypoints are fixed reviewed controller operations, not general evidence-JSON CLI switches.

## Exact facts the controller must obtain

For every candidate/evidence promotion, directly query and validate:

- Canonical repository identity, authorized task/command and exact intended default branch; immutable candidate commit/tree, code closure, data/protocol/policy/model/evidence hashes.
- PR repository/base/head, actual current head SHA, all changed paths, merge state and merged commit. Reject fork/unexpected repository, head movement, draft/closed-unmerged state and out-of-scope changes.
- Required CI workflow identity/path and its reviewed definition; exact run ID, attempt, triggering event, tested SHA/tree, completed conclusion, required jobs/steps. Distinguish PR synthetic merge SHA from head SHA: prove tested tree/parents match the intended candidate+base or rerun at exact reviewed revision. A green run on a different commit or unrelated workflow is irrelevant.
- Latest effective review submissions bound to exact candidate revision; dismissed/stale reviews do not count. Independent verifier artifact must bind its own execution to the candidate/input/protocol hashes. A GitHub review and an independent scientific reproduction are separate evidence.
- Activation-intent PR's final reviewed head and actual merged commit, plus ancestry/tree mapping into default branch. When squash/rebase is used, compare the relevant content tree/closure; do not require the old head SHA to remain an ancestor when Git semantics do not guarantee that.

Available connector methods include fetch_pr, list_pull_request_reviews, list_pull_request_review_threads, fetch_commit, compare_commits, fetch_commit_workflow_runs, fetch_workflow_run_jobs/steps/logs and artifact fetch/download. Their existence is not proof every field/permission is available. In particular, fetch_commit_workflow_runs is documented to return only PR-triggered first-page runs; it cannot prove exhaustive main-CI state. Jobs/artifact wrappers also have first-page/latest-attempt limitations. Combined status is not automatically a complete check-run/workflow history.

Verified existing alternative (parent capability probe): `mcp__codex_apps__github_fetch` explicitly supports approved GitHub REST workflow-run collections/subresources as authenticated GET and returns JSON unchanged. The parent's actual `actions/runs/36759583636` fetch succeeded and exposed candidate head SHA beginning `61d79`, workflow `.github/workflows/data-intake-tests.yml`, event `pull_request`, attempt 1, success and PR #28 head/base bindings. Its actual `actions/runs?branch=main&per_page=5&page=1` fetch succeeded, returned total_count 23 and included main push CI run 36744155390, success at baseline SHA beginning `c1acabe`. Thus main CI is observable through an existing authorized interface without new permissions. These facts are parent-supplied observed probe evidence, not a new probe executed by this reviewer. Parent retains complete raw probe receipts/exact SHAs.

Use that verified fetch operation for exact run IDs and needed jobs/attempt subresources, and bounded explicitly paginated collections for discovery. A five-item first page does not establish exhaustive history; track pages, response counts/total_count, query constraints and termination. Prefer direct exact-run verification once an ID is known. A pagination limit reached without resolving required facts yields an incomplete-facts blocker, never inferred success. Distinguish each run attempt and its actual tested SHA/tree; the baseline main success does not validate a newer candidate. Read exact returned fields and retain their source URL/operation in receipts. Do not broaden permissions or accept caller JSON as a substitute. Freeze the exact required CI policy before activation; PR CI is never mislabeled main CI.

Persist fetched fact receipts with source operation, IDs, relevant normalized fields, observation time and digest for audit. These persisted receipts alone are not portable authentication. Their trusted meaning comes from the controller's actual fetch and the reviewed activation path; production must verify the intent's repository provenance rather than trusting a copied receipt from arbitrary input.

## Reviewed intent and atomic remote activation

Separate a reviewed immutable ActivationIntent from its eventual ActivationEvent to avoid self-referential commit hashes and backdated activation.

Intent binds operation PROMOTE/ROLLBACK, candidate/model/composite hashes, expected previous event hash, gate/reproduction bundle, code/policy closure, task/job IDs and allowed scope. It is proposed/reviewed/CI-checked/merged through the existing PR path. The intent never claims it has already activated or contains its own future merge SHA. Model/evidence bytes are immutable.

After verifying actual merge/review/CI facts and rerunning/rechecking gates as required, the fixed controller activation operation creates the event containing intent hash, authentic merged-commit reference, expected previous event, next model, verified code closure, gate bundle and actual activation observation time. Never activate at model-training/freeze/PR-creation time. Event publication must occur before a subsequent issuance can select it.

A practical remote CAS uses a dedicated append-only registry ref with existing contents permission, while all activation intents remain reviewed in main. Fetch current registry ref SHA S and validated current event E. Build one commit C with **exactly S as sole parent**, adding immutable event and updating pointer; require requested expected_previous==E. Update ref to C with force=false. Because C has S as its direct parent, a competing different child of S makes the second update non-fast-forward and fails; do not merge/rebase/retry that stale transition silently. On response ambiguity refetch: C present means idempotent success, another child means conflict. If registry ref absent, use an actual create-if-absent ref operation and verify its semantics; connector create_branch description says 'create or update', so inspect/test this before assuming atomic genesis.

The connector update_ref exposes force=false but no explicit expected-old-SHA; the direct-parent construction above is essential. Never call that API 'CAS' for an arbitrary descendant commit. PR merge expected_head_sha protects only head movement, not expected base/event. Therefore using that option alone for registry CAS is insufficient.

Dedicated registry ref is production state, not arbitrary report data. Only the fixed authorized transition may write it; ordinary report publication must be path/ref-scoped away from it. Readers verify every event traces to an actual reviewed intent and matching trusted gate operation. No new protection configuration is assumed: existing credential holders remain within the stated trust boundary. If repository policy forbids a state ref, an alternative main-only design needs verified serialization plus merge/base precondition enforcement; do not substitute a read-then-merge race for atomicity.

Rollback requires a previously validated/activated model, compatible reviewed inference code closure and current applicability/safety. It appends a new event through the same reviewed operation; no old event or ORIGINAL is edited. A past validation does not permit running an obsolete unsupported adapter under changed code unnoticed.

## Issuance, concurrent promotion and ORIGINAL immutability

At issuance, obtain current validated registry commit/event and actual issuer time, lock local version allocation, verify all input availability and selected code/model closure, execute actual composite inference, and freeze generated output. Full inference bundle/output/component receipts are hashed. Generic external freeze cannot acquire official Champion provenance merely by supplying identical IDs.

A local flock does not serialize different runners. Remote publication must be append-only and bound to a current registry/version state. Best minimal design serializes both activation and issuance commits on the same production state ref: issuance commit adds immutable ORIGINAL artifact/receipt (or a hash-bound durable artifact reference) and version-index update with direct-parent CAS, retaining same current Champion pointer. If activation wins the race, stale issuance commit fails, prospective times and version are revalidated and inference is redone against newly selected model. If issuance wins, its selection event is unambiguous; later promotion affects later issuance only. Never publish a failed-CAS artifact as ORIGINAL or reuse a consumed version with different bytes.

If final ORIGINAL artifacts are maintained on another required repository ref, use the state-ref issuance reservation/commit record as authoritative before mirroring via PR, and clearly mark pending persistence until durable bytes are available. Two independent unconditional branch writes are not one atomic freeze. Do not claim full publication atomicity until the chosen durable layout is implemented and tested.

Official operational scoring checks verified issuance provenance from this authenticated repository/event chain, source/inference hashes, actual prospective issuance and immutable version binding. It does not infer authenticity from payload fields. Historical external ORIGINAL/recovered predictions retain existing provenance limitations without any byte rewrite. Hash all protected existing raw/ORIGINAL before/after every live acceptance.
