# GORIQ-compatible Risk Gate and Human Gate

## Purpose

Habu AI uses the same execution-gating semantics as GORIQ so the current Chat-based workflow can later move to GORIQ without redefining approval behavior.

This specification does not weaken the repository rules in `AGENTS.md`. In particular, raw-file preservation, evidence requirements, temporal leakage controls, branch/test/PR workflow, and secret-handling rules remain mandatory.

## Execution loop

For an in-scope goal, continue through:

`Goal -> Plan -> Execute -> Verify -> Repair/Replan -> Write-back -> Next Action`

Repeat until the goal is complete or a Human Gate is reached. A Pull Request by itself is not a reason to stop when the change is eligible for automatic continuation under this specification.

## Risk classes

### LOW

Routine, reversible work fully covered by existing specifications and repository rules.

Examples:
- ingesting GPX or Habu logs through the existing intake pipeline;
- SHA-256, byte-size, duplicate, format, and timestamp auditing;
- writing evidence generated by those audits;
- adding records that conform to an already-approved data schema;
- deterministic regeneration of derived artifacts.

LOW work may continue automatically after required verification succeeds.

### MEDIUM

Bounded changes that remain inside existing requirements but require stronger verification because they affect derived datasets, evaluation, or implementation behavior.

Examples:
- rebuilding 100m x 10-minute Exposure;
- regenerating features from approved sources;
- rerunning existing walk-forward evaluations;
- localized implementation fixes that do not alter requirements, permissions, dependencies, workflows, governance, or security posture.

MEDIUM work may continue automatically only after tests/CI and the applicable independent verification succeed.

### HIGH

Work requiring owner approval before execution or continuation.

Examples:
- changing an approved requirement, canonical data definition, label semantics, operational-night rule, KPI, model-evaluation rule, or governance rule;
- destructive or irreversible changes;
- overwriting or deleting `data/raw/`;
- changing authentication, authorization, repository permissions, secrets handling, or security controls;
- initiating paid external actions or material new recurring cost;
- material production/external side effects outside already-approved behavior.

HIGH work stops at Human Gate.

### CRITICAL

Work that must not be executed automatically, including actions that would expose credentials/secrets, deliberately bypass security controls, or perform an unauthorized destructive action.

CRITICAL work is blocked.

### UNKNOWN

If risk cannot be classified confidently, treat it as HIGH and stop at Human Gate.

## Human Gate behavior

A Human Gate must state:
1. the exact proposed action;
2. why it is HIGH or UNKNOWN;
3. affected paths/systems;
4. whether the action is reversible;
5. the minimum owner decision required.

Do not request approval for LOW/MEDIUM work merely because a PR exists.

## Verification and continuation

Automatic continuation requires all checks mandated by the repository and the affected specification to pass. Failure enters `Repair/Replan`; it does not silently relax tests, requirements, evidence, security, or governance.

If a safe bounded repair remains inside LOW/MEDIUM scope, repair and verify again. If repair would require widening scope into HIGH/UNKNOWN, stop at Human Gate.

## Habu data application

Routine intake follows:

`incoming/ -> SHA-256/duplicate/format/time audit -> data/raw/ -> evidence/ -> branch -> CI/tests -> PR -> eligible continuation`

The promotion step must preserve raw bytes and all `AGENTS.md` constraints.

For multiple individual Habu associated with one observation/capture event, use the repository's approved event/individual two-layer schema once that schema exists on `main`. Adding conforming records is LOW/MEDIUM. Creating or changing that canonical schema is HIGH unless it has already been explicitly approved and encoded in repository requirements.

## Precedence

1. Explicit owner instruction for the current goal.
2. `AGENTS.md` and approved repository requirements/specifications.
3. This gate specification.
4. Implementation convenience.

No lower-precedence rule may broaden authority or weaken a higher-precedence constraint.
