## 4. Codexの具体的実装レーンと順序

### Gate A：現物監査・再現（モデルやプロンプトはまだ変更しない）

- PR HEADを固定して関連Actionsのrun/job/ログを読み、6例と40例の正本、計算指標、コード差分、テスト数を再現する。
- ベースのデータ原本やコード全体を無差別に取得しない。レビュー品質専用のallowlistと人工コードのみ使う。
- 指摘が正常コードにも発生する原因を「入力の文脈欠落」「JSON出力・引用行の誤り」「ありもしないエラーの推測」「小型モデルの能力不足」「評価器のバグ」に分解し、それぞれ証拠を添えて分類する。
- 単純なケースで、なぜ正常なコードにも1件出すかを再現し、モデル出力と判定器でどの段階で止めるべきかを特定する。
- Gate Aの成果物はベースライン表、原因別Gap Matrix、変更してはいけない不変条件。読んだだけで「改善済み」と報告しない。

### Gate B：審査品質システムの設計とテスト先行の修復

- 指摘生成器と証拠検証器を分離。AIは未確定候補と具体的な再現主張を出し、別の信頼された実行器が検証する。コード引用照合、構造化出力、原因説明の検証、独立結果、候補の昇格ゲートを明確にする。
- behavioral_evidence.pyの契約を維持・拡張し、少なくとも case/source hash/仕様根拠/具体的入力/claimed actual/claimed required/引用/検証実行の証拠ハッシュを整合させる。データ型、NaN、時刻、例外、未実行、想定外の副作用をfail-closedにする。
- Qwenの出力が自由記述だけなら自動でconfirmed bugにしない。合格させる目的で、AIが出さなかった再現入力・出力を後からQwen自身の回答として補完しない。
- 単純なスタイル指摘、文字列・コメントだけを証拠とする指摘、定義済み関数の未定義誤認、HTMLの存在する終了タグの欠落誤認、GPS時刻境界、本人捕獲統計の誤計上、保存ACK誤認を回帰試験にする。
- 失敗するREDテストを先に追加し、原因に絞った最小修正、GREEN、既存テスト全通過、変更範囲の独立レビューを繰り返す。
- まず既存の許可済みQwen1.5B + localhost Ollamaの範囲で品質改善する。小型モデルそのものの変更が必要なら、1.5Bで未達のエビデンス、想定する最小代替、計算資源と追加費用0円の根拠、セキュリティ影響を整理する。根幹のモデル方針変更はHuman Gateとして事前承認を得る。

### Gate C：開発データと「本当に未見」の独立評価を分離

- 既存固定40例は開発・回帰の診断専用に降格。これを何回試しても未見精度とは呼ばない。Git blobを維持。
- 評価設計担当を実装担当と分離。問題仕様と正解を実行可能なオラクルで独立確認し、Python/JS、正誤、行番号ずれ、境界値、例外、データ保全、既知のセキュリティ問題などの層別テストを用意する。
- **本当の未見評価**では、最終モデル・プロンプト・検証器・採点器・依存環境のバージョンをFreezeし、その後に独立評価担当が未見ケースを確定し、ラベルをモデル入力・開発用ログから隔離して採点。合成コードだけを使用する。
- 最低40件（不具合20以上／正常20以上）の未見問題、重大な保存データ欠損や位置漏洩の既知欠陥を少なくとも含むこと。検証不能な問題は評価済みと偽らず、分母と欠測理由を保存。問題の難度が不適切なら、初回結果を保全した上で独立の新版として管理する。採点後に内容を変更して同一版と呼ばない。
- GitHubで公開されるファイル、既知の過去ログ、Codexへ渡した仕様と開発用固定40件を「未見問題」に再利用しない。独立にラベル隔離できない環境なら評価はUNSEALED_HOLD、合格禁止。

### Gate D：数値と第三者性のある合格判定

事前に閾値・母集団・例外を固定する。最低限の目標値：
- Precision（独立実証で正しいと判定された発行指摘／発行指摘の全件）95%以上。
- Recall（確認済み欠陥のうち発見できた割合）80%以上。
- 正常ケースへの偽警告率5%以下。
- 保存データ欠落・本人誤計上・座標公開等の指定した重大欠陥の見逃し0件。
- 全件の判定区分、引用照合、欠測、棄権、重複、無意味な指摘、要求仕様不明を明記。
- 実モデル推論ログ、digest、プログラム/プロンプトSHA、GitHub HEAD、ケースSHA、独立再現テスト、raw/filtered/published結果を同じ版に紐付ける。
- 小数の閾値達成は過学習や未見一般化を保証しない。標本数と不確実性を記述する。
- 6例のスモーク実モデルPASS、開発40例の結果を含む回帰PASS、真の未見評価PASS、別の実行主体による独立安全レビュー、全CI PASSが揃うまでQUALITY_QUALIFIEDと呼ばない。
- 同じCodexが書き、同じCodexが評価して自己承認する構成は禁止。許可済みの別モデル／別実行担当がいない場合はINDEPENDENT_REVIEW_BLOCKEDを返す。

### Gate E：安全統合・継続

- 全ての変更を小さなbounded sliceに分け、各sliceで仕様・失敗テスト・実装・ローカル回帰・GitHub Actionsの**最新HEAD成功**を確認。
- 実行可能な独立ワーカーがある場合だけ並列化。担当ファイルを分け、モデル・採点・セキュリティ・統合で同一ファイルを同時編集しない。独立ワーカーがない場合は1タスク内で順番に実行し、並列実行したと偽らない。
- 同じPR #136の同じブランチを修正。頻繁な連続pushでCIがキャンセルされるので、単位をまとめてcommitし、完了したHEADの結果を得てから次へ進む。自身が直接pushできない環境ならコミットと検証結果を残し、同じPRへ反映する手順を明示する。新規PRを作らない。
- 本番統合・公開は本タスクに含めない。品質合格後、Ownerの明示承認が必要な変更はSTOPする。
- チャットやPRにモデルが実際に何をしたか、何件評価したか、どう失敗したか、再現証拠、未完了のブロッカーを正確に報告する。計画だけ作って終了しない。

## 5. 重要なアンチ・チート回帰テスト

- 既存v1のソースと正解を変更したらFAIL。Git blob照合を必須とする。
- 全件指摘するAI、全件棄権するAI、引用行だけ一致して説明が嘘のAI、既知40件を丸暗記したAIは最終未見ゲートでFAIL。
- 空のfindingsを成功扱いしたとき、欠陥のRecallが0ならFAIL。
- JSONが壊れた、source hashが違う、期限切れGPS、型が違う、モデルが自分で作った期待値を独立の正解と扱う、独立証拠のない長い説明でバグ確定とする場合はFAIL/HOLD。
- コメント行の引用だけから実装の不具合認定をしない。文脈や定義の欠けたdiffから未定義と断言しない。
- モデル出力コードの実行、外部アクセス、秘密情報の公開、ブランチ権限の格上げ、課金は安全停止。
- Qwen推論と審査テストが失敗でも、模型テスト（mock）の成功で本物のAI品質を合格と報告しない。
